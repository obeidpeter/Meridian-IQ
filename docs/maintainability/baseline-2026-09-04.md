# Maintainability Baseline - 2026-09-04

## Scope and Method

The baseline covered all first-party workspaces, architecture and decision
records, OpenAPI/code generation, DB schema and migrations, authentication and
request context, background work, external rails, Clerk AI, web/mobile apps,
tests, CI, release scripts, and Replit runtime configuration.

Evidence came from repository scans and executed commands, not file names or
documentation claims. Generated code and build output were separated from
hand-written source where the metric allowed it.

## Baseline Results

| Measure                           |            Before change |
| --------------------------------- | -----------------------: |
| First-party source files          |                    1,214 |
| First-party source lines          |                  265,306 |
| Files over 600 lines              |                       90 |
| Files over 1,000 lines            |                       20 |
| Exact duplicate groups/files      |                  27 / 83 |
| Relative-import cycles            |                        6 |
| Functions with complexity over 10 |                      339 |
| Functions with complexity over 20 |                       83 |
| Maximum observed complexity       |                      148 |
| Deterministic tests               | 1,135 passing, 0 failing |

The six cycles crossed Clerk eval/growth/red-team, invoice service/approval,
rail adapter/fault/HTTP transport, and format notification/index boundaries.
The highest server orchestration hotspot was release readiness at complexity 78. Large UI pages and pipeline/domain modules dominate file-size debt.

## Build and Tooling

- `pnpm run typecheck`: passed.
- `pnpm run lint`: passed.
- `pnpm run build`: failed because all five Vite configs required hidden
  `PORT` and `BASE_PATH` variables. Recursive build also coupled the web/API
  build to an environment-specific Expo artifact.
- `pnpm exec prettier --check .`: reported 1,965 files. A repository-wide
  formatting change was rejected because it would obscure functional review.
- Production dependency audit: no unignored high/critical finding. Two high
  image-size advisories were covered by the existing documented Metro-only
  OSV exception.
- Outdated inventory: patch/minor updates exist for Clerk and XML tooling;
  major migrations exist for Vite, Vitest, Zod, OpenAI, Pino, and Expo. Bulk
  upgrades were not safe to combine with structural work.

## Test and Operational Evidence

The database-free suites covered shared libraries, mobile, five web apps, and
role-specific console/SME behavior. The latest GitHub CI run on the starting
revision also passed API/database tests, schema and guardrail migrations,
migration rollback, restore drill, production builds, and Playwright journeys.

## ISO/IEC 25010 Assessment

| Characteristic | Baseline assessment                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Modularity     | Strong domain grouping, weakened by six cycles and large pages/modules.                                                |
| Reusability    | Shared contract, format, and UI packages are mature; local UI wrappers remain duplicated.                              |
| Analysability  | Extensive comments/tests, but no root README, environment inventory, ADR index, or executable graph rule.              |
| Modifiability  | Contract-first and migration discipline are strong; hidden build inputs and coupled policy lists increase change cost. |
| Testability    | Broad suites and DB/E2E CI are strong; pure release decisions and build profile resolution lacked focused tests.       |

## Primary Risks

1. A dependency cycle could make initialization order observable in critical
   invoice, rail, or Clerk paths.
2. Request transaction and model-rate policy could drift between middleware.
3. A new contributor could not reproduce the documented root build.
4. High-complexity release decisions were hard to test without infrastructure.
5. Large page/domain modules, global format debt, and major dependency
   migrations remain expensive sources of regression risk.
