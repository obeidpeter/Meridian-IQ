COMPONENT + DESIGN-SYSTEM INVENTORY

(1) What exists and where

Shared package lib/web-ui (imported as @workspace/web-ui, exports in lib/web-ui/src/index.ts): `triggerDownload` (lib/web-ui/src/trigger-download.ts); `ClerkDock` body (clerk-dock.tsx); `NotificationFeed` — the full-page bell-feed list markup (notification-feed.tsx); a "workspace" module (workspace.tsx) with `WorkspaceHeader`, `MetricStrip`/`Metric` (tone-aware stat tiles via `mi-*` CSS classes in styles.css), `SegmentedControl` (role=tablist filter pills), `WorkQueue` (toned priority list with built-in empty state), and `CommandMenu` (hand-rolled Ctrl+K palette with focus restore + arrow-key listbox); hooks `useUrlTab`, `useActionPolicyControls`, `useClerkActionsDialog`, `useFilePicker`, `usePageTitle`, and the toast store `useToast`/`toast` (use-toast.ts) which every app re-exports via its own `src/hooks/use-toast.ts` shim.

Per-app shadcn ui/ dirs: artifacts/sme-compliance/src/components/ui/ (17 files: alert, alert-dialog, button, card, dialog, input, label, popover, select, sheet, skeleton, spinner, switch, textarea, toast, toaster, tooltip); artifacts/console/src/components/ui/ adds checkbox, progress, tabs (20 files); artifacts/buyer-portal/src/components/ui/ has its own subset with table, pagination, toggle/toggle-group, checkbox, progress but NO dialog, popover, tabs, or switch; artifacts/landing/src/components/ui/ is just button/card/input/label.

App-level shared components. SME (artifacts/sme-compliance/src/components/): empty-state.tsx, query-error.tsx, skeleton-list.tsx, feature-unavailable.tsx, page-header.tsx, capability-gate.tsx, stale-build-banner.tsx, notification-bell.tsx, field-error.tsx (inline form error + `invalidClass`), pill-toggle.tsx (aria-pressed filter pill), row-status-icon.tsx, file-picker-button.tsx, clerk-dock.tsx wrapper, require-session/require-client-scope. Console (artifacts/console/src/components/): empty-state.tsx, query-error.tsx, feature-unavailable.tsx, capability-gate.tsx (adds `RoleGate` + AccessDenied with role identity and "Switch account"), stale-build-banner.tsx, notification-bell.tsx, stat-tile.tsx, status-light.tsx (InvoiceStatusLight traffic dot + reasons popover), catalogue-select.tsx, clerk-dock.tsx wrapper, plus ~20 domain cards; `ClerkPageHeader` hides inside clerk-shell.tsx. Buyer-portal: feature-unavailable, query-error, stale-build-banner, notification-bell, layout, require-session only — no empty-state/page-header. Vocabulary + status tones live in lib/format/src/index.ts (plus notifications.ts, filing-copy.ts, wht-copy.ts, notice-copy.ts, action-copy.ts, onboarding-copy.ts), each app shimming through `src/lib/notifications.ts`.

(2) Duplicated near-identical per-app components

- All 17 shadcn ui/ files shared by SME and console are byte-identical (verified by diff) — a wholesale copy that only drifts by console's extra checkbox/progress/tabs; buyer-portal re-implements its own variants.
- empty-state.tsx: SME vs console identical except one comment line ("mirrors the SME app's component").
- feature-unavailable.tsx: identical in all three of SME, console, buyer-portal.
- query-error.tsx: console's adds an optional `detail` diagnostic prop (HTTP status line, testid text-error-detail); SME and buyer-portal (identical to each other) lack it — a real drift: SME/buyer users can't distinguish stale-build 404s from faults.
- stale-build-banner.tsx: three copies with behavioral drift — console persists dismissal per server version in sessionStorage and uses role="alert"; SME uses plain component state and role="status"; wording differs ("Ask your administrator…" vs "Restart the api-server workflow…").
- notification-bell.tsx: three siblings sharing lib/notifications vocabulary but drifting structurally — SME uses Radix Popover + loading skeletons + error copy + close-on-navigate; console renders nothing at all unless the query succeeds (no loading/error state) and uses different badge colors (bg-teal-700 vs bg-primary); buyer-portal hand-rolls its own popover panel because its ui/ dir has no Radix popover.
- capability-gate.tsx: SME's is a slimmed console copy; console's richer AccessDenied (who you are, switch-account escape hatch) never made it back to SME.
- clerk-dock.tsx wrappers in SME and console are the intended thin-wrapper pattern (shared body in web-ui), differing only in context/suggestion copy — the model the others should follow.

(3) Missing primitives a usability pass would want

- No `badge.tsx` in any ui/ dir — every status pill is a raw string of classes from lib/format helpers or hand-rolled spans; a `<Badge tone>` wrapper would give consistent semantics (and a place for sr-only text).
- No breadcrumbs anywhere (grep "Breadcrumb" returns nothing); detail pages (console client-detail.tsx, SME invoice-detail.tsx) improvise ArrowLeft back-links.
- No shared ConfirmDialog: alert-dialog.tsx primitives exist but each of the 8 consuming pages re-assembles title/description/destructive-button boilerplate.
- No shared PageHeader in console: 21 console pages hand-roll `<h1 data-testid="text-page-title">` with slightly varying classes (e.g. billing.tsx:234 vs advisory.tsx:510) while SME has page-header.tsx and web-ui has WorkspaceHeader — three competing header recipes.
- No inline form-error primitive outside SME: field-error.tsx (FieldError + invalidClass) exists only in SME and is used on just 2 pages; console forms (client-detail, api-access, billing, whitelabel, statements) handle aria-invalid ad hoc with no aria-describedby error text.
- No SkeletonList outside SME: console pages stack raw `<Skeleton>` runs inline (platform-ops.tsx and client-detail.tsx each 5x).
- No table primitive in SME/console (buyer-portal has ui/table.tsx); no dropdown-menu, no pagination outside buyer-portal, no toast "action" conventions documented.
- web-ui's CommandMenu, WorkQueue, MetricStrip exist but console's stat-tile.tsx duplicates Metric's job with a different tone axis — two stat-tile systems.

(4) How status colors/badges are done today

The canonical system is lib/format/src/index.ts §8: `BadgeTone` (emerald/teal/violet/amber/blue/red/slate), `PILL` recipe + `TONE_CLASSES` (each tone ships light+dark), `pillClasses(tone)`, plus semantic mappers `statusTone`/`statusLabel`/`badgeClasses` (exhaustive over the contract's InvoiceStatus — e.g. stamped→emerald, pending→amber, failed→red), `severityBadgeClasses`, `confirmationLabel`/tones, and the borderless `summaryPillClasses("amber"|"emerald")` for card-header counts. Channel badges for bells come from lib/format/src/notifications.ts (`channelBadgeClasses`), re-exported through each app's src/lib/notifications.ts shim. Consumers are widespread: SME pages (invoices.tsx, invoice-detail.tsx, dashboard.tsx, filings.tsx, wht.tsx, bills.tsx, obligations.tsx, reconciliation.tsx, recurring.tsx, consent.tsx), console cards (filings-card.tsx, wht-card.tsx, obligations-card.tsx, onboarding-card.tsx, billing-statement-card.tsx, statement-connections-card.tsx) and console pages (client-detail.tsx, control-centre/shared.tsx, clerk*.tsx, advisory.tsx, api-access.tsx, platform-ops.tsx, invitations.tsx), and buyer-portal invoice-respond.tsx. Outside the pill system: console/src/components/status-light.tsx maps a server-computed green/amber/red to bg-green-500/amber-500/red-500 dots (note: green-500, not the emerald family the pills use); console/src/components/stat-tile.tsx defines its own VALUE_TONE (success/warning/danger → emerald/amber/red text) and iconTone recipes; web-ui's Metric/WorkQueue use a parallel tone vocabulary ("positive/warning/critical/info") resolved in lib/web-ui/src/styles.css `mi-*` custom properties; SME row-status-icon.tsx pins text-emerald-600/text-destructive icons. So there are four coexisting tone vocabularies (BadgeTone strings, StatTile success/warning/danger, web-ui positive/critical, status-light green/amber/red), consistent in hue family but not in naming or API, and no component wrapper enforcing the pill markup.
